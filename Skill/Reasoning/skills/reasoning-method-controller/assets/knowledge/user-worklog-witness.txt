# AI transport protocol

Each AI session should receive one generated feeder and should return zero or more file blocks.

```text
<<<PPC_FILE path="relative/path.ext">>>
file content
<<<PPC_END_FILE>>>
```

Rules:

- Paths are relative to project root.
- No `..` and no absolute paths.
- Structured primitives must be valid JSON.
- Do not return source code during discovery/planning unless the feeder explicitly requests a probe.
- Preserve IDs already present in requirements, tensions, invariants, and decisions.
- State changes should be proposed through `.ppc/state-proposal.json`; the CLI remains authoritative for gates and phase advancement.
- A repair session must not rewrite passing areas unless a demonstrated dependency requires it.

# PPC architecture

PPC v0.1.0 has a scanner, bootstrap compiler, topology/strategy resolver, context compiler, script materializer, and AI transport layer.

## 1. Sanitized scanner

`host -> sanitized provenance + capability evidence`

The scanner captures toolchain facts before initial AI planning while preserving the privacy boundary. It supports capability, targeted, and explicit-opt-in full inventory depths.

## 2. Bootstrap compiler

`intake + scan -> control-plane filesystem + repository aliases + primitive slots`

The project workspace is not itself assumed to be the product repository. Existing repositories may remain elsewhere; only `.ppc/private/repos.runtime.json` stores their raw paths.

## 3. Topology / strategy resolver

`host provenance + target matrix + providers + integrations -> provisional execution strategy`

The resolver can recommend native execution, Docker/Linux, multi-platform builds, WSL, remote CI, or provider-specific tooling. Its output is provisional evidence, not an irreversible architecture decision.

## 4. Context compiler

`public project primitives + current state + phase -> minimal sanitized feeder`

It chooses current phase instructions, relevant structured primitives, applicable adapters/SKILLs, and current verification/repair evidence. Private runtime state is never an input.

## 5. Script materializer

`.ppc/script-plan.json -> run-task.py + thin .ps1/.sh wrappers`

AI reasons about project-specific commands from topology/toolchain evidence; PPC owns path resolution and wrapper materialization.

## 6. AI transport

AI responses are untrusted patch packages. PPC previews file blocks, rejects unsafe/protected paths, then applies only with explicit `--apply`.

## Authority summary

- `.ppc/private/**`: local-only operational state.
- `.ppc/environment/host.snapshot.json`: scanner evidence.
- `.ppc/state.json` and approvals: PPC workflow authority.
- `.ppc/topology.json` / targets/providers/integrations: topology contracts/IR.
- `docs/`: human-readable product/system/decision artifacts.
- `@repo/<alias>/**`: runtime implementation authority.
- Git: historical change authority.
- generated feeder files: disposable transport, never project truth.

# Environment model

PPC separates **provenance**, **target compatibility**, **execution substrate**, **provider/service**, and **integration/transport**.

`host.snapshot.json` answers: *where and with what capabilities is this project currently being worked on?*

`targets.json` answers: *where must the resulting artifact execute or remain compatible?*

`topology.json` answers: *what nodes and boundaries constitute the project?*

`execution-strategy.json` answers: *given provenance + targets + constraints, what is the least-friction build/execution strategy?*

A project created on Windows may intentionally target Linux; a Mac ARM host may build Linux AMD64 through Docker Buildx or remote CI. Creation provenance must never silently narrow product compatibility.

# Evidence policy

Evidence source depends on project mode.

## Greenfield

Start from problem/context/use cases. External open-source references may be used to find approaches and heuristics. Search budget is a saturation heuristic, not a sacred count: stop when additional sources add no materially new pattern; continue when the candidate architecture is still changing.

Classify references as:

- `stem`: a plausible architectural lineage for the project;
- `borrow`: a specific heuristic/module/pattern worth taking;
- `filter`: an approach explicitly rejected, with reason.

## Existing repo / bugfix

Start from local evidence:

1. repository structure and manifest files;
2. reproduction/failure signal;
3. tests, logs, issues, and recent diffs/history;
4. relevant source path and dependency boundaries;
5. external references only when local evidence leaves a material unknown.

This avoids doing greenfield research when the repository itself is the primary evidence source.

# Formal model

PPC models project work as typed transformations rather than a pile of documents.

```text
Source input
  -> Evidence
  -> Normalized primitives
  -> Candidate plans
  -> Hard-constraint elimination
  -> Comparative selection
  -> System contract
  -> Small probe / architecture witness
  -> Approval gate
  -> Full implementation
  -> Verification
  -> Repair or release/handoff
```

## Three normative levels

1. **Global constitution**: reusable rules of the compiler/work method.
2. **Project constitution**: constraints and bans specific to this project.
3. **Task/phase instruction**: what the current AI/agent is asked to do.

These answer *where a rule gets authority*.

## Invariant propagation

Invariant propagation answers a different question: does an important rule/decision remain represented through later transformations?

```text
OBS-004 -> DEC-002 -> INV-003 -> SRS-007 -> TEST-005
```

The chain need not be fully formal, but every critical invariant should point to its origin and verification evidence.

## Closure semantics

A phase may advance only when its required outputs exist, blocking gates are approved, and structural verification does not report a fatal error. This gives AI work a termination condition rather than an open-ended impulse to keep restructuring.

# File ownership model

PPC separates:

- **authority** — source of truth for a fact;
- **maintainer** — who/what may change it;
- **generation** — authored/generated/mirrored/external;
- **AI transportability** — whether it may appear in a feeder.

The strongest boundary is `.ppc/private/**`: it exists only so local tooling can resolve real repository locations and other operational details. It is CLI-owned, ignored by project Git, protected from AI ingest, and excluded from prompt compilation.

Scanner-owned host provenance is similarly protected from AI mutation. AI may challenge the interpretation of scanner evidence through decisions/execution strategy, but may not rewrite the observed snapshot.

# Scanner privacy boundary

AI-facing scanner output is sanitized by construction. PPC does not intentionally collect environment-variable values, credentials, tokens, SSH keys, hostname, username, IP/MAC addresses, or cloud account/tenant/subscription identifiers. Raw local repository paths are stored only in `.ppc/private/repos.runtime.json`, which is excluded from AI feeders and project Git.

Scan depth:

- `capability` (default): recognized compilers, interpreters, package managers, shells, IDE/CLIs, container and cloud CLIs; versions only.
- `targeted`: capability scan + repository dependency declarations + only tools/packages requested in `.ppc/toolchain-request.json`.
- `full`: opt-in installed-package inventory for supported managers. Use only when the diagnostic value exceeds fingerprinting/noise cost.

Cloud account queries are not performed by the core scanner. Presence/version of a CLI is evidence of a capability, not evidence of authentication or permissions.

# Script primitives

Script primitives are project operations, not fixed shell files. Typical primitives are `doctor`, `bootstrap`, `dev`, `build`, `test`, `verify`, `deploy`, and `handoff`.

AI writes `.ppc/script-plan.json` using repository aliases and platform/execution-context variants. `ppc generate-scripts` materializes a cross-platform Python runner and thin `.ps1`/`.sh` wrappers. The compiler never injects credential values.
