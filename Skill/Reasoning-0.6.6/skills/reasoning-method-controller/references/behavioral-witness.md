# Behavioral Witness: Desired Reasoning-Worklog Pattern

This file captures the user's examples of the **kind of controlled work progression** the skill should induce. It is not a script and not a demand to expose private chain-of-thought. Treat each line as a high-level, auditable operation summary.

## Core pattern

A strong worklog often progresses through these kinds of moves:

- Reconstructing the requested deliverable before choosing a method.
- Separating the primary route from secondary/mixed inquiry components.
- Comparing reference conversation data against extracted messages.
- Piecing together earlier session summaries and contracts.
- Identifying behavior patterns rather than merely copying wording.
- Auditing the user's claim that a prior sketch or skill was wrong.
- Explaining why a `SKILL.md` merely duplicated the source contract.
- Checking frontmatter for ambiguity between description and behavior.
- Distinguishing a printed trace or output shape from a real action gate.
- Examining concrete failure examples before generalizing.
- Detecting jumps from evidence collection to architecture.
- Testing whether a platform-support claim follows only from source inspection.
- Detecting invented environment details such as a fabricated Windows username/path.
- Withdrawing a criticism when timing/context evidence defeats it.
- Auditing licensing constraints that materially affect a recommendation.
- Defining the bounds of a claim before evaluating it further.
- Converting descriptive guidance into executable operational rules.
- Auditing user premises rather than automatically amplifying them.
- Adding references only when they resolve a material unknown or decide a live rival.
- Verifying references before presenting them as support.
- Requiring operational definitions before building metrics or scores.
- Distinguishing apparent architecture from evidence-backed architecture.
- Preserving valid findings while rejecting unsupported extensions.
- Running a discriminating probe or witness before closing when one can change the design.
- Revising the route when new evidence changes the inquiry jurisdiction.
- Repairing the earliest failed dependency rather than polishing downstream prose.
- Designing red-team cases that test the behavioral contract.
- Separating generic method from user-specific style adapters.
- Separating core method from domain adapters and knowledge packs.
- Validating the package after writing it.

## Style of the observable trace

Preferred trace items are:
- concise;
- action-oriented;
- specific about the object being checked;
- tied to an actual stage transition, test, source operation, or revision;
- willing to report reversals;
- free of generic filler;
- numerous enough to show trajectory in long work, but not so numerous that they become raw internal monologue.

Good:

```text
Reconstructing the actual deliverables before choosing the comparison criteria.
Rejecting the compatibility claim because only source inspection supports it.
Running a minimal probe against the load-bearing runtime assumption.
Verifying the dataset license before retaining it as a candidate.
Revising the critique after the timestamp establishes the opposite chronology.
Closing provisionally because one evidence position remains unavailable.
```

Bad:

```text
Thinking about the problem.
Reasoning more deeply.
Considering some options.
Now I am in S4 OPERATE.
I think this probably works.
```

## Important interpretation

The worklog is **observability over a method**, not the method itself. The method must independently enforce:

```text
route selection
intent reconstruction
premise audit
authority assignment
dependency analysis
material-unknown prioritization
research gate
hard-constraint elimination
probe/falsification
verification
reversal
closure/change-condition
repair-to-earliest-failed-dependency
```

Do not print stage labels mechanically. User-visible progress should describe the substantive action and finding.
