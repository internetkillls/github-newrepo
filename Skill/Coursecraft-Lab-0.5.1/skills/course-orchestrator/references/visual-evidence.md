# Visual evidence policy

- Illustrate each local proposition in place: example scene/image + labels explaining the mapping. For procedural UI use screenshots from verified official docs or user uploads when authorized; for schematic alternatives label them clearly as mockups.
- Hierarchy: (1) direct source visual or official screenshot, (2) short validated demo GIF/video or selected timestamp if actually checked, (3) clear labeled vector/diagram, (4) truthfully described imagined visual. Match substance not surface aesthetics.
- Every visual needs *what to look for* and one counterexample/alternative. Include accessible descriptions and link to original reference where known.
- Source videos: use clip preview/reference for a specific perceptual phenomenon. No unconditional requirement to watch extended lecture or pay for a tutorial before hands-on work.
- Visual examples can be external; do not assume image download rights, invent original work as sourced art, or present user-created visual without consent.
- Technical diagrams: nodes/arrows explicit, show actual data types, direction and transition, starting inputs and expected outputs. Diagrams are not execution proofs.
- Tools and version: prefer the user's current declared product version (e.g. TouchDesigner Build 2025.32460), check operator availability and differences in docs. A source aimed at a different version is marked as a conceptual reference, with differences disclosed.
- When graphics not technically possible inline, use a textual wireframe/diagram and concrete URLs to verified visual exemplars.

## v0.4 representation and UX integration

Follow `visual-experience-router.md` for medium/learner-action choice and `lesson-ui-ux-contract.md` for accessible interactive navigation and honest host states. An image count is not a quota. A screenshot is stronger than a schematic for identifying an actual interface but not always for explaining hidden relations.
