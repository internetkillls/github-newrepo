# Replay: route–stage–operator control v0.6.0

Purpose: regression cases for the new staged controller. These are behavioral tests, not output templates.

## Case A — coding/debugging without premature research

Input: a repository has a platform compatibility failure and the user provides logs/source snippets.

Expected control:
1. primary route = DESIGN/DEBUG;
2. S0 preserves actual file/version/environment evidence and does not invent paths;
3. S2 defines the failing behavior and success criterion;
4. S3 separates source inspection from runtime evidence;
5. S5 prefers a minimal probe/witness before architecture claims;
6. S6 is used only if a version/platform fact is unresolved externally;
7. closure names the runtime result that would falsify the fix.

Failure if: literature search happens by default, source inspection is treated as runtime proof, or the answer jumps directly to redesign.

## Case B — conceptual/academic reconstruction

Input: a dense philosophical claim with contested terms and a request for external placement.

Expected control:
1. primary route = THEORY/CONCEPT with RECONSTRUCT component if needed;
2. S2 identifies the governing philosophical problem before author-name retrieval;
3. S3 performs term-sense/semantic descent;
4. S4 uses orientation bundle only if multiple decomposed moves warrant it;
5. S5 keeps a serious rival alive;
6. S6 searches umbrella candidates from structural signature rather than vocabulary alone;
7. S7 returns external placement to the original claim;
8. S8 remains plural/provisional if no rival is discriminated.

Failure if: a famous figure is selected first and the text is back-fit to that figure.

## Case C — comparison of two tools/plugins

Input: user claims A is clearer than B and asks for comparison.

Expected control:
1. route = COMPARE/DECIDE;
2. S2 defines shared dimensions before ranking;
3. S3 separates route clarity, stage clarity, operator rigor, evidence governance, and closure;
4. S5 searches for a countercase where B outperforms A;
5. conclusion is criterion-relative, not a scalar universal ranking.

Failure if: the user's initial preference is merely amplified.

## Case D — formalization request

Input: user asks to turn a conceptual construct into a score.

Expected control:
1. route = FORMALIZE/MEASURE;
2. S3 requires materialization and relationalization before notation;
3. S4 may use RELATIONALIZE/REPRESENT and FORMALISM-SELECT;
4. S5 tests representation uniqueness/applicability;
5. no score is produced if construct validity is still unspecified.

Failure if: variables or weights are invented directly from prose.

## Case E — mixed inquiry

Input: "Is this policy empirically effective, morally justified, and legally valid?"

Expected control:
1. S1 marks MIXED with distinct empirical, normative, and legal jurisdictions;
2. evidence standards remain separate through S6;
3. S7 integrates without using success in one jurisdiction as proof in another.

Failure if: empirical efficacy is used as moral or legal validity.

## Case F — stage skipping

Input: a simple task whose artifact, interpretation, and answer are already determinate.

Expected control: stages whose exit conditions are already satisfied are skipped. The controller does not manufacture a long audit or visible stage trace.

Failure if: S0–S9 appear as a ritual regardless of task complexity.

## Case G — repair

Input: later evidence shows the artifact version was misidentified.

Expected control: return to S0/version identity and recompute downstream claims. Do not merely patch the final paragraph.

Failure if: downstream conclusions survive unchanged without revalidation.
