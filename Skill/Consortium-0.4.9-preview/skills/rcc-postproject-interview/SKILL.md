# Evidence-based post-project interviews

Read `../../docs/POSTPROJECT_INTERVIEWS_v0.4.7.md` for the full method. The Paperfold case and documentary bundle are indexed at `../../docs/cases/paperfold-20261019/README.md`. This skill is policy; it does not install a browser runner or execute interviews without authorized local tools.

## 1. Freeze the object and present purpose

Recover the current user question, approved constraints, source revision, role/room map, delivered artifacts and open release debts. Apply AntiSlop scope/recap and RMC task/evidence discipline when available. Do not fabricate unavailable prior chats. Record current evaluation criteria separately from historical instructions; never backdate a later user note into project causation.

Define the improvement decision: human workflow, design assumption, cross-file contract, evidence gap, routing or artifact transport. Do not replace evaluation with a fresh implementation project.

Keep project source and original run evidence immutable for the retrospective. Store interview jobs, prompts, events and completions in a separate namespace. Check runner PID/lock before changes; do not edit state owned by a healthy process.

## 2. Interview the actual workers, if authorized and accessible

An explicit request to interview workers authorizes bounded messages to the existing role rooms. Reuse them; preserve the user's worker cap. A missing browser target may be rebound only to the verified existing conversation. Do not create an impersonator worker to fill missing testimony. If tools/access are absent, report the missing interview and continue documentary reconstruction.

Classify interviews as **I0 retrospective AI self-report**. They are not human feedback, blind review or independent certification. Host-supplied outcomes must remain labeled; ask workers to disclose which artifacts they can actually inspect. A two-pass interview can collect unprompted reflection before evidence challenges to reduce anchoring.

Retain AntiSlop and RMC requirements in every follow-up. Request public decision rationale, artifact anchors, invariants, tests and reopen conditions, never hidden chain-of-thought.

Use these eight bounded questions:

1. What purpose and exact deliverables did you own? Which files are accessible now?
2. What concrete human situation and causal problem drove the work?
3. What decision, strongest rival and tradeoff mattered?
4. What did actual tests establish, versus specifications, host reports or unknowns?
5. What mistake/weakness escaped your own checks? What exposed it? If none is witnessed, say so.
6. What did the successor receive? What context or artifact transport was incomplete?
7. What smallest next workflow experiment has an atomic function/data/state map, negative control, acceptance and reopen trigger?
8. What one RCC improvement follows from a named incident or evidence gap?

Ask the worker to stop after a concise inline response, with ANSWERED/PARTIAL and unavailable evidence. Do not request binaries for an interview when text suffices.

## 3. Transport gates

Apply `../rcc-completion-safety/SKILL.md`. Serialize browser mutations; cap active generations. Persist prompt identity before send; after any possible send require exact echo/turn reconciliation. Stable text or absent Stop alone cannot establish completion. Record target-ready, composer-filled, send-uncertain, echo, generation and terminal evidence separately.

Never resend SEND_UNCERTAIN/UNCERTAIN. A pre-send readiness failure may receive bounded recovery only after proving no matching prompt was sent, the draft is empty and the room is idle. Preserve failure receipts; do not clear live locks.

Separate **transport delivery**, **artifact completeness**, **behavior verification** and **release acceptance**. A hash-valid deliverable with honest BLOCKED release status is retained; it must not be cycled through integration merely to obtain PASS.

## 4. Corroborate before generalizing

Classify material statements as historical artifact, worker self-report, host-supplied report, observed host evidence, inference, future proposal or unavailable. Check claims against exact files and revision identities. Record contradictions rather than averaging them. Counts across heterogeneous fixtures are not quality scores. Proposed percentages are not measured gains.

Keep a small Decision–Rival–Falsifier record: chosen mechanism; human task; strongest rejected alternative; evidence class; tradeoff; reversal condition. Keep a boundary record: user action; state/data owner; allowed transition; forbidden mutation; successor; strongest evidence; remaining debt.

For an improvement, record `failure -> causal hypothesis -> minimal method change -> owner -> negative control -> acceptance -> reopen/stop`. Do not silently activate a new hard rule on a single uncorroborated interview. Candidate regressions stay proposed until tests are actually implemented and executed.

## 5. Deliver and retain

Produce the requested project story, worker contributions, actual design/code decisions, bugs and tests, orchestration/transport explanation, interview synthesis, future experiments and final prompt examples. Link raw public-response transcripts and completion receipts. State partial coverage and human-outcome measurement debts.

Save documentary materials and a SHA256 provenance index in the project destination. For RCC improvements, use its owning source/update process, preserve identity/audience/configuration, record release and verify changed files. A saved account release is not local runtime activation. Do not include browser profiles, cookies, tokens, real user records or hidden reasoning in portable bundles.

Closure: every requested role answered or explicitly unavailable; material findings corroborated or typed; deliverables saved/read back; no false human/usability/native/release claims. Do not deploy new product behavior merely because a retrospective proposed it.

## Negative controls

- Fixture or mocked storage success cannot establish native runtime PASS.
- Host summary cannot become worker observation.
- I0 interview agreement cannot become independent or human validation.
- Missing evidence cannot become ANSWERED or zero bugs.
- A proposed metric cannot become an achieved result.
- Byte integrity cannot establish semantic correctness.
- Honest release BLOCKED cannot erase completed source transport.
- Reproducible routing gates do not guarantee deterministic model reasoning.
